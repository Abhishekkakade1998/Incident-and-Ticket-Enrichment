# Design Decisions

| # | Decision | Why | Trade-off |
|---|---|---|---|
| 1 | **Two MCP servers** (alarm management, ticketing) instead of one | Separate credentials, blast radius and ownership; the ticketing server holds the only write tools and the approval verification. | One more process to run. |
| 2 | **Python + official MCP SDK (FastMCP, `mcp` 1.x)**, Streamable HTTP, stateless, JSON responses | Typed tools from Pydantic signatures give input and output JSON Schemas for free; stateless HTTP scales horizontally and keeps per-request trace headers simple. Pinned `<2` because 2.x renamed the APIs. | A short-lived MCP session per tool call (initialize + call). Fine locally; pooling is a future improvement. |
| 3 | **The copilot never calls source APIs.** It only holds MCP tokens; MCP servers hold source tokens | Matches the assignment's MCP boundary and gives a clean credential boundary. | Extra hop. |
| 4 | **Deterministic intent rules + code-defined workflows** rather than letting an LLM choose tools | Predictable, testable, offline and auditable chains for an operational domain where a wrong write is costly; entities are still resolved dynamically through MCP (no hard-coded assets). | Less flexible on unusual phrasings; an LLM planner over the discovered catalog is a future option (the registry already exposes schemas). |
| 5 | **Offline grounded composer as default; LLM optional and citation-validated** | The system runs and passes tests with no API key; when Claude is enabled, its prose is accepted only if every citation exists, so the LLM cannot introduce unsupported claims. | Offline prose is template-like. |
| 6 | **Hashing embedder + BM25 hybrid, JSON index** | Reproducible offline ingestion and CI, no model download, no vector-DB container; good relevance on a domain corpus with RRF + metadata rerank. | Weaker semantic recall than neural embeddings; the `Embedder` / `VectorIndex` seams make the swap cheap. |
| 7 | **Evidence-weighted cause analysis** (sources must mention a cause; rank by number of agreeing sources) | "Likely cause" is the riskiest output; requiring evidence and showing the sources makes it reviewable. | Uses a domain vocabulary (`CAUSE_LEXICON`); new failure modes need terms added. |
| 8 | **Priority reconciliation** between the alarm-system score and ESC-001 rules, using the more urgent band and flagging the conflict | Conflicting evidence is surfaced instead of hidden; safer default. | May over-prioritise; the human reviewer decides. |
| 9 | **HMAC approval token bound to the payload + idempotency key** | Explicit confirmation is enforced in the MCP server, not just the UI: replay with another payload, forged tokens and LLM- or document-initiated writes are rejected; retries never duplicate tickets. | Shared signing key between backend and ticketing MCP (a KMS / signed JWT with key rotation in production). |
| 10 | **Uniform `ToolCallRecord` instead of exceptions** in the MCP client | Partial failures become data: the orchestrator degrades to `partial`, the GUI shows exactly which step failed and why. | Callers must check `status`. |
| 11 | **Dependency-free GUI** (vanilla JS, no build) | No Node toolchain needed; fewer supply-chain dependencies; easy to serve from nginx or the backend. | Less component structure than React; acceptable at this size. |
| 12 | **Simulator with fault injection** | Retry, timeout and degraded-mode behaviour is demonstrable and testable end to end. | Test-only endpoint; it is behind the same bearer auth. |
| 13 | **SQLite audit log, in-memory conversations** | Minimal persistence that still gives a durable audit trail. | Conversations are lost on restart and not shared across replicas (Redis in production). |
